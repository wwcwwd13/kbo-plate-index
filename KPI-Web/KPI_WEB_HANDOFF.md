# KBO Plate Index(KPI) 웹페이지 인수인계 문서

작성 목적: 새로운 Codex 작업에서 이 문서만 먼저 읽어도, 지금까지의 대화 맥락과 웹페이지 제작 방향을 이해하고 이어서 작업할 수 있도록 한다.

이 문서는 KPI v3의 계산식을 다시 정의하는 문서가 아니다. 이미 계산된 KPI 결과를 사용자가 보기 쉽고 납득하기 쉬운 화면으로 보여주는 일을 위한 작업 메모다.

## 1. 프로젝트 이름

- 정식 명칭: **KBO Plate Index**
- 약칭: **KPI**
- 일반적인 `Key Performance Indicator`와 혼동될 수 있으므로, 이 프로젝트에서는 항상 `KBO Plate Index`의 약칭으로 사용한다.

## 2. KPI로 하고 싶은 일

KPI는 단순히 선수에게 숫자 하나를 붙여 줄 생각으로 시작한 것이 아니다.

야구에서 한 선수가 타석에 들어서고, 그 결과가 경기의 기대 득점과 흐름에 영향을 준다. 그 흐름 속에서 선수의 평가가 시간에 따라 어떻게 움직이는지, 그리고 특정 시점의 선수·구단 평가가 어느 정도인지 한눈에 보고 싶다.

다만 일반 사용자에게 모든 내부 계산과 타석 원자료를 보여주려는 것은 아니다. 내부에서는 타석 단위 계산을 사용하더라도, 외부 화면에서는 최종적으로 정리된 **구단별 Rating 표**를 중심으로 보여주고 싶다.

웹페이지가 전달해야 할 핵심 메시지는 다음에 가깝다.

> “현재 KBO에서 각 구단의 선수들이 어떤 평가를 받고 있으며, 그 평가는 시간에 따라 어떻게 움직였는가?”

Rating이라는 단어보다, 타석과 경기 흐름에서 파생된 지표라는 느낌을 주는 이름으로 KPI를 사용한다.

## 3. 외부 화면에서 우선 보여주고 싶은 것

현재 1차 목표는 작고 명확한 화면이다.

### 기본 화면

- 마지막에 정리한 **구단별 KPI Rating 표**를 중심으로 한다.
- 전체 타석 로그 표는 외부 기본 화면에 보여주지 않는다.
- 타석별 before/after 값과 각종 내부 변수는 계산 검증용 자료로 보관하되, 초기 공개 화면에는 노출하지 않는다.
- 구단·리그·1군/2군/잔류군을 구분해서 볼 수 있으면 좋겠다.
- 선수 이름, 소속, Rating, 순위 또는 구단 내 위치가 한눈에 들어오면 좋겠다.

### 시간 그래프

표만 고정해서 보여주는 것보다, 시간이 지나며 KPI가 어떻게 움직였는지 볼 수 있는 그래프가 있으면 좋겠다.

아직 그래프의 최종 형태를 확정한 것은 아니다. 다음과 같은 방향을 우선 검토한다.

- 가로축: 날짜 또는 경기 진행 순서
- 세로축: KPI Rating
- 구단별 Rating의 시간 흐름
- 필요하면 특정 구단을 선택했을 때 해당 구단의 변화 추이
- 추후 선수 상세 화면을 만들 경우, 선택한 선수의 Rating 변화 추이

마우스를 올리면 날짜, 구단, Rating, 변화량 등을 확인할 수 있으면 좋겠다.

## 4. 기존 시트에서 참고할 부분

기존 외부용 Google Sheet의 구단별 Rating 표가 시각적 참고자료다.

참고 시트:

<https://docs.google.com/spreadsheets/d/1RFlizhPk7cyzsh2J2WIKFtAaoumYJ61yz95cXxUMacg/edit?gid=387297493#gid=387297493>

시트 작업 중 다음과 같은 표현·정리 방향이 논의되었다. 웹페이지에서 그대로 복제해야 한다는 뜻은 아니며, 우선 참고할 디자인 언어다.

- Rating과 이름은 읽기 쉽고 정돈된 형태로 표시한다.
- 순위가 중요한 곳에는 색으로 상위·하위권을 빠르게 구분한다.
- 1군과 2군은 명확히 분리한다.
- 1군 구단 표에는 9명 평균을 사용할 수 있다.
- 2군에는 9명 평균을 반드시 넣을 필요가 없으며, 현재 시트에서는 삭제된 상태를 기준으로 생각한다.
- 등록·활동 상태가 불확실하거나 최근 기록이 오래된 선수는 회색으로 표시하는 방식이 사용되었다.
- 중복 선수는 이름만 보고 구분하지 말고 선수 ID, 소속 구단, 1군/2군 구분으로 식별해야 한다.

세부 색상, 글꼴, 행 높이 등은 웹페이지에 맞게 다시 설계해도 된다. 기존 시트의 모양을 기계적으로 복사하는 것이 목적은 아니다.

## 5. 데이터에 대한 기본 태도

- KPI 계산 모델과 웹페이지 표시 부분은 분리한다.
- 웹페이지는 Rating을 새로 계산하거나 임의로 보정하지 않고, 최신 계산 결과를 읽어서 표시한다.
- 원자료와 모델 결과는 보존하고, 웹페이지용 데이터는 별도로 가공한다.
- 선수를 합칠 때 이름만으로 병합하지 않는다. 선수 ID와 역할, 구단, 1군/2군 정보를 함께 확인한다.
- 원자료에 없는 정보를 화면에서 추측해 채우지 않는다.
- 나중에 데이터가 갱신되더라도, 이전 결과와 비교할 수 있도록 날짜·버전을 남기는 편이 좋다.

현재 확인된 최신 통합 타석 자료는 다음 파일이다.

- `outputs/kbo_v3_20260913_refresh/KBO_Rating_v3_plate_appearance_integrated_before_after.csv`

이 파일은 내부 검증과 향후 웹용 데이터 생성의 원천 자료로 사용한다. 다만 웹페이지 첫 화면에 이 전체 파일을 그대로 읽히는 방식은 피하고, 구단 표와 그래프에 필요한 작은 데이터 파일을 별도로 만들 가능성이 높다.

## 6. 웹페이지 제작 방향

현재 웹페이지는 React + Vite 기반이다. GitHub Pages에 올릴 수 있는 정적 빌드 구조를 유지하면서, 로컬과 배포 환경 모두 API 서버가 제공하는 JSON 응답으로 SQLite를 읽도록 구성했다. 로컬 API가 아직 시작되지 않은 경우에만 기존 임시 JSON을 참고용으로 사용하며, 공개 배포 환경에서 API가 없거나 실패하면 오래된 표 대신 빈 상태를 표시한다.

현재 역할은 다음과 같다.

- React: 화면 컴포넌트와 UI 상태 관리
- Vite: 개발 서버와 정적 배포용 빌드
- CSS: 표·선수 페이지의 시각 디자인
- `src/data.js`: 임시 JSON과 로컬 API 사이의 데이터 접근 경계
- `KPI-Backend/api/`: private backend의 `database/kpi.db`에서 선수 프로필·Rating 스냅샷·타석 기록을 읽는 로컬 API
- `KPI-Backend/database/images/`: KBO ID 파일명으로 저장된 선수 프로필 이미지
- Apache ECharts/React 이벤트: 경기별·타석별 Rating 그래프, 경기별 X축 확대, 점 hover·focus·click 상세 tooltip
- `data/sheet_reference.json`: 로컬 API가 아직 시작되지 않았을 때만 사용하는 개발용 참고 표

경기별 그래프는 Apache ECharts의 `dataZoom`으로 X축 표시 범위를 조정한다. `최근 1개월`과
`전체` 보기만 제공하며, 그래프 높이와 Y축 눈금은 고정하고 확대·드래그는 X축에만 적용한다.
`markArea`로 Rating 구간 배경을,
`markLine`으로 최고점 기준선을, HTML tooltip으로 경기·타석 상세를 표시한다.
ECharts 청크는 선수 페이지에서만 지연 로딩되어 메인 표와 변동표의 첫 번들에 포함되지 않는다.

현재는 `index.html`, `player.html`, `diff.html`을 각각 Vite 진입점으로 사용한다. 실제 SQLite는 브라우저에서 직접 읽지 않고, 개발 환경에서는 `http://127.0.0.1:5050`, 배포 환경에서는 `VITE_API_BASE_URL`로 지정한 API를 통해 읽는다. `start-dev.cmd`를 실행하면 로컬 Vite와 API를 함께 시작할 수 있고, GitHub Pages workflow에는 Fly.io API 주소가 빌드 환경으로 설정되어 있다.

메인 구단 표는 `GET /api/team-ratings`가 SQLite의 `player_rating_snapshots`를 기준으로 자동 구성한다. 쿼리 파라미터 `date=YYYY-MM-DD`를 주면 해당 날짜 이하에서 가장 최근인 선수 Rating을 기준으로 표를 만든다. 응답에는 `meta.asOf`, `meta.modelVersion`, `1군`·`2군`·`잔류군` `sections`, 구단별 타자·투수 배열, 9명 평균이 포함된다. 각 선수 항목에는 `gray`와 별도로 최신 로스터 이벤트 기준의 `medicalStatus`(`injury_list`, `rehab_list`, `foreign_player_rehab`)와 날짜·비고가 올 수 있다. `gray`는 Rating 모델의 기존 표시 플래그이고 부상·재활 상태와 같은 의미로 합치지 않는다. 프런트의 `fetchTeamRatings({ date })`가 이 API를 호출하며, 로컬에서만 API가 없을 때 `data/sheet_reference.json`으로 fallback한다. 공개 배포 환경에서 API가 없거나 실패하면 빈 상태를 표시한다. 배포 환경에서 API를 연결할 때는 `VITE_API_BASE_URL`을 사용한다.

KPI 변동표는 `diff.html`에서 제공한다. `GET /api/rating-diff-dates`가 데이터 범위 안의 날짜와 날짜별 경기 수를 반환하고, `GET /api/rating-diffs?date=YYYY-MM-DD`가 선택한 경기일의 출전 선수만 반환한다. 응답은 1군·2군을 모두 포함하며, 선수별로 경기 종료 후 `rating`, 당일 `ratingDelta`, 역할별 기록 요약(`summary`), 타석별 상대 선수·결과·변동량(`plateAppearances`)을 제공한다. 경기 수가 0인 날짜를 선택하면 구단 헤더는 유지하고 선수 영역은 빈칸으로 표시한다. 프론트에서는 Rating 셀에 현재값과 `▲/▼ 변동량`을 두 줄로 보여주며, 선수명에 마우스를 올렸을 때만 역할별 요약과 타석별 상세를 표시한다. 툴팁에는 경기 번호를 표시하지 않는다.

현재 메인 표 구성 규칙은 다음과 같다. 2025년 KBO 정규시즌 순서(`LG → 한화 → 삼성 → SSG → NC → KT → 두산 → 롯데 → KIA → 키움`)를 고정 정렬 기준으로 사용하고, 고양은 키움 2군으로 묶는다. Rating에 존재하는 선수는 최근 출전 여부와 관계없이 모두 표에 남긴다. 현재 등록 스냅샷 또는 최신 `call_up` 이벤트로 확인되는 선수는 `1군`, 최신 `demotion` 이벤트로 확인되는 선수는 `2군`, 그 외 선수는 `잔류군`으로 분류한다. 현재 DB에는 별도의 완전한 2군 등록 스냅샷이 없으므로 퓨처스 배치는 `demotion` 이벤트를 우선 사용한다. 최신 부상자·치료/재활 이벤트가 현재 로스터 상태보다 같거나 뒤에 있으면 `잔류군`으로 두고 `medicalStatus`·날짜·비고를 표시한다. 이후 콜업·등록 등 후속 상태 이벤트가 더 최근이면 이전 부상 상태는 현재 표시에서 해제한다. 부상·재활 표시는 이름 옆 `†`와 마우스오버 설명으로 제공하며, 비고에 들어온 재활 기간도 함께 보여준다. 1군 표에는 타자·투수 각각 9명 평균과 18명 평균·추정 전력 순위를 표시한다.

현재 연결 범위:

- `player_rating_snapshots`: 선수별 날짜 Rating 그래프와 표
- `pa_rating_effects`: 선수별 타석 기록의 Rating before/after/delta
- `people`, `players`, `external_player_ids`, 로스터 스냅샷: 선수 기본 정보
- `batting_stat_snapshots`: 데이터가 있는 선수만 타격 통계를 표시
- `KPI-Backend/database/images`: KBO ID와 파일명을 매칭해 선수 프로필 사진을 표시
- `player_rating_snapshots`: 메인 구단 표의 선수별 Rating과 구단·리그 grouping에 사용
- `team_rating_snapshots`: 향후 구단 Rating 자체를 별도 스냅샷으로 제공할 때 사용할 수 있음

선수 링크는 이름만으로 연결하지 않는다. 로컬 API의 `/api/players/link-map`에서 역할·구단·리그·Rating을 함께 확인해 `playerId`를 정하고, `npm run enrich:links`로 정적 표 데이터에 반영한다. DB에서 확인되지 않는 선수는 다른 선수 페이지로 잘못 연결하지 않는다.

## 7. 예상되는 첫 화면 흐름

아직 확정 디자인은 아니지만, 다음 흐름이 가장 자연스럽다고 생각한다.

1. 페이지 제목: `KBO Plate Index`
2. 리그 또는 1군/2군 선택
3. 구단별 KPI 표 표시
4. 구단을 선택하면 시간에 따른 KPI 그래프 표시
5. 필요하면 선수 목록 또는 선수 상세 화면으로 확장

처음부터 모든 기능을 넣기보다, 표와 그래프가 한 화면에서 자연스럽게 보이는지 확인하는 것이 우선이다.

## 8. 아직 확정하지 않은 것

다음 항목은 아이디어 단계이며, 실제 제작 중 더 나은 방향이 있으면 바꿔도 된다.

- 구단 표의 정확한 열 구성
- 구단 Rating의 시간 그래프를 어떤 기준으로 집계할지
- 1군·2군을 한 화면에 함께 보여줄지, 탭으로 나눌지
- React 컴포넌트의 세부 화면 구성과 그래프 기능 확장
- GitHub 저장소와 배포 방식을 언제 도입할지
- 기존 Google Sheet의 스타일을 어느 정도까지 반영할지

## 9. 새 작업에서 지켜야 할 우선순위

새 Codex 작업은 이 문서를 먼저 읽고, 다음 순서로 진행한다.

1. KPI가 무엇을 보여주려는 프로젝트인지 이해한다.
2. 기존 모델의 수식을 불필요하게 다시 설계하지 않는다.
3. 외부 기본 화면은 구단별 Rating 표로 시작한다.
4. 시간축 그래프를 추가한다.
5. 표와 그래프의 가독성을 먼저 확인한다.
6. 데이터가 정상적으로 연결된 뒤에만 복잡한 프레임워크나 서버 도입을 검토한다.

가장 중요한 것은 KPI를 복잡한 모델의 결과물처럼 보이게 만드는 것이 아니라, 사용자가 구단과 선수의 평가 흐름을 직관적으로 이해할 수 있게 만드는 것이다.

## 10. 향후 제품 계획 초안

현재 메인 화면은 구단별 Rating 표를 중심으로 유지한다. 아래 내용은 다음 단계에서 확장할 기능에 대한 아이디어 메모이며, 세부 화면과 우선순위는 실제 데이터를 연결하면서 조정한다.

### 선수 상세 화면

- 메인 표의 선수명을 클릭하면 선수 개인 화면으로 이동한다.
- 공개 가능한 선수 기본 정보(선수명, 정식 소속 구단명, 역할·포지션, 현 소속, 생년월일)를 보여준다.
- 투수는 `투수`, 타자는 `야수 · 내야수`처럼 역할과 포지션을 하나로 표시하며, 포수도 `야수 · 포수`에 포함한다.
- 현 소속은 `1군`·`2군`·`잔류군`으로 표시한다.
- 경기별 KPI Rating 변화 그래프를 제공한다.
- 역할에 맞는 타격 또는 투구 기록을 별도 카드로 보여주고, 반대 역할의 `playerId`가 연결된 경우 해당 기록 화면 이동 버튼을 제공한다.
- 경기 기록은 원시 경기 키 대신 상대 구단·홈/원정·구장을 표시하고, 타격/투구 전용 성적 열로 나눈다.

### 날짜별 구단 Rating

- 특정 기준일을 선택하면 해당 날짜의 구단별 Rating 표를 확인할 수 있게 한다.
- 현재값만 덮어쓰지 않고, 날짜·버전별 스냅샷을 보존해 과거 결과와 비교할 수 있게 한다.

### Diff 보기

- 특정 날짜를 선택하고 직전 기준일 또는 비교 기준일과의 차이를 보여준다.
- 해당 날짜에 있었던 경기와 타석 기록을 함께 확인한다.
- 기록에 따라 선수·구단 Rating이 어떻게 등락했는지 변화량과 함께 표시한다.

### 등록·말소 및 상태 이력

- 선수 등록, 말소, 1군·2군 이동 등 로스터 상태 변화를 별도 영역에서 확인할 수 있게 한다.
- 이 기능을 추가할 때는 상태 변경일, 선수 ID, 구단, 이동 유형을 안정적으로 연결할 수 있는 데이터 구조가 필요하다.

### 권장 확장 순서

1. 선수명 링크와 선수 상세 기본 화면
2. 선수별 날짜 KPI 그래프
3. 날짜별 구단 Rating 스냅샷
4. 경기·타석 기록을 포함한 Diff 화면
5. 등록·말소 및 1군·2군 이동 이력
